문제 A — 장부를 Gaussian이 아니라 공간 셀 단위로 저장

설계 완료

원본 구현은 coverage_counts[gaussian_id, direction_bin] — Gaussian 하나하나마다 독립된 방향 관측 이력을 저장한다. 문제는 3DGS가 학습 중 계속 Gaussian을 분裂/복제/삭제한다는 것: Gaussian 번호가 바뀌거나 없어지면 그 행(row)의 이력이 통째로 무효화된다. nbv_gym은 이걸 "매번 전체를 다시 렌더링해서 처음부터 다시 쓴다"는 제일 비싼 방식으로 회피했다.

제안된 방향

Gaussian 번호 대신 3D 공간을 성긴 셀(voxel)로 나눠서 "이 셀이 어느 방향에서 관측됐는가"만 저장한다. Gaussian 개수는 장부에 넣지 않고, 후보 뷰를 채점하는 순간에만 "그 셀에 지금 Gaussian이 몇 개 있는가"를 가중치로 곱해서 점수를 합산한다. Update(장부에 기록)와 score(가중 평균)를 분리하는 게 핵심.

이 분리가 좋은 이유: update 시점엔 Gaussian 개수를 몰라도/추적 안 해도 된다 — "이 셀, 이 방향, 봤음/안 봤음" 이진 플래그 하나면 끝. 개수 가중치는 필요할 때(=채점할 때) 그 순간의 최신 Gaussian 분포에서 즉석으로 계산하면 되니, 장부 자체는 densify/prune이 아무리 일어나도 전혀 건드릴 필요가 없다.

Gaussian 단위 vs 셀 단위

기준 Gaussian 단위 (원본) 셀 단위 (제안)
장부 크기 Gaussian 수에 비례 (~59만행, 계속 변함) 셀 수에 비례 (씬 스케일로 고정, 훨씬 작음)
densify/prune 시 영향 관련 행 전부 무효화 → 재구축 필요 셀 자체는 안 바뀜 → 장부 그대로 유지
update 연산 Gaussian마다 개별 기록 터치된 (셀, 방향) 쌍에 이진 플래그만
score 연산에 필요한 것 Gaussian 위치 → 방향 벡터 셀 중심 → 방향 벡터 + 셀별 Gaussian 개수(즉석 계산)
정밀도 점 단위, 정밀함 셀 크기에 따라 손실 있음 — 크기 선정이 관건

동작 순서

01
뷰 V가 실제로 학습될 때 (update) V에서 보이는 Gaussian들 (VIGS render()의 radii>0로 이미 앎) → 각 Gaussian의 현재 3D 위치를 셀 id로 양자화 → V의 관측 방향에 해당하는 bin 계산(뷰당 1회) → 이번 스텝에서 새로 터치된 (셀, bin) 쌍에 이진 플래그 set.
02
후보 C를 채점할 때 (score) C가 볼 것으로 예상되는 셀들 파악(셀 중심점만 절두체 테스트 — Gaussian 전체를 투영하는 것보다 훨씬 쌈) → 각 셀마다 "C의 방향 vs 그 셀의 기존 관측 방향들" 코사인 유사도 계산(기존 공식 그대로, 대상만 셀로 바뀜) → 셀별 점수를 그 셀의 현재 Gaussian 개수로 가중 평균 → C의 최종 novelty 점수.
확정 — 희소(sparse) 셀 할당

씬 bounding box 전체를 미리 통짜 격자로 쪼개두지 않는다. Gaussian이 실제로 있는 셀만 그때그때 장부에 등록한다(hash 기반, 처음 등장하는 셀 좌표면 그 순간 새 행 추가). 이유 두 가지: (1) 실제 씬은 표면 근처에만 Gaussian이 있고 나머지는 빈 공간이라 통짜 격자는 대부분 낭비된다. (2) 더 근본적으로, VIGS는 카메라가 계속 새 공간으로 이동하며 지도가 실시간으로 넓어지므로 "씬 전체 범위"가 학습 시작 시점엔 존재하지도 않는다 — 미리 격자를 깔 기준 자체가 없다. GPU 구현은 Python dict 대신 torch.unique로 현재 점유 셀 좌표 집합을 뽑고 torch.searchsorted로 행 인덱스를 찾는 방식이 자연스럽다. 아직 Gaussian이 없는 미탐험 영역은 장부에 아무 정보가 없는 게 맞는 동작 — "어디를 새로 볼지"는 이 점수의 역할이 아니라 VIGS의 keyframe/dense view 등록 로직이 이미 처리하는 별개 문제.

아직 정해야 할 것 (열린 질문)

  1. 셀 크기 — 아래 "확정" 섹션 참고 (0.10m 고정 상수로 결정됨).
  2. Gaussian이 최적화 중 이동하면서 셀이 바뀌는 문제. 분裂/삭제뿐 아니라 gradient step으로 위치 자체가 계속 조금씩 바뀐다. 이건 셀 id를 캐싱하지 않고 매번 현재 위치에서 즉석 계산하면 자연히 해결된다(양자화 연산 자체가 매우 쌈) — 다만 "절대 캐싱하지 말 것"을 설계 규칙으로 명시해둬야 나중에 누가 최적화한답시고 캐싱했다가 조용히 버그 나는 걸 막을 수 있다.
  3. 셀별 Gaussian 개수 갱신 시점, 방향 기준점, 저장 방식, bin 개수 — 아래 "확정" 섹션 참고 (전부 결정됨).

확정 — 언제, 얼마나, 어디까지 채점할지

4개 결정 완료

VIGS 코드 조사(carve_prune.py, distCUDA2, IMU rescale 로직) + 4개 질문에 대한 답으로 확정. 넷 다 "정확도보다 단순함/실시간 비용"을 우선한 선택 — 각각 알려진 단점은 후속 과제로 남겨둔다.

버퍼 시작 시점 — IMU 초기화 이후부터

VIGS는 IMU 초기화(video.IMU_initialized) 전까지 좌표 스케일이 임의값이고, 초기화 시점에 지도 전체가 gs.rescale(s)로 한 번에 리스케일된다(코드 조사로 확인). 고정 셀 크기(미터 단위)가 의미를 가지려면 리스케일 이후여야 하므로, 버퍼는 IMU_initialized=True로 전환되는 순간부터 빈 상태로 시작한다. 알려진 단점: 초반 몇 초~수십 프레임은 coverage 점수가 없다 — 이 구간은 weighted_mix가 기존 방식(균등/카운트 비례)으로 폴백해야 함, 별도 처리 필요.

채점 범위 — 최근 N개 슬라이딩 윈도우

등록된 후보 전체가 아니라 최근 N개(예: 200)만 매번 채점한다. 비용이 O(N)으로 고정되고 학습 길이와 무관해져서, 프레임이 계속 들어오는 온라인 환경에서 채점 비용이 시간이 지날수록 불어나는 문제(coverage 벤치마크에서 본 것과 같은 종류)를 원천 차단한다. 알려진 단점: 아주 오래전에 등록됐지만 아직 안 뽑힌 후보는 윈도우 밖으로 밀려나 영영 재평가 안 될 수 있다 — 실제로 문제가 되는지는 VIGS의 후보 등록/소멸 로직을 봐야 판단 가능, 후속 확인 필요.

Occlusion 처리 — Frustum만, occlusion 무시

후보 채점 시 카메라 절두체(시야각) 안에 있는 셀은 다 "본다"고 치고, 실제로 다른 물체에 가려졌는지는 따지지 않는다. 기하학적 테스트만 필요해서 저렴함. 알려진 단점: 벽 뒤 셀도 "보인다"고 잘못 채점될 수 있다 — 오차 크기는 씬 구조에 따라 다름(막힌 방이 많을수록 커짐). 학습된 뷰 자체는 VIGS의 실제 렌더러(정확한 가시성)로 학습되니 이 오차는 순수하게 스코어링(어느 뷰를 고를지) 단계에만 영향.

셀 크기 — 고정 상수 0.10m

carve_prune.py가 비슷한 목적(occupancy 채점)에 이미 쓰고 있는 값을 그대로 따른다 — 검증된 값이고 구현이 단순하다. 알려진 단점: 좁은 방과 넓은 홀처럼 씬 스케일이 크게 다른 경우 최적이 아닐 수 있다. 문제가 실제로 드러나면 distCUDA2 기반 씬별 동적 계산으로 바꿀 수 있도록 여지는 남겨둠(코드상 상수 하나만 바꾸면 되게 설계).

셀별 Gaussian 개수 갱신 — densify_and_prune 호출 직후에 훅

매 score() 호출마다 새로 계산(가장 정확, 비용 최소지만 근거 없이 잦음)도 아니고 임의 타이머로 캐싱(고정 비용이지만 densify와 무관한 시점이라 stale해도 이유가 없음)도 아니라, Gaussian 개수가 실제로 바뀌는 유일한 이유인 densify_and_prune 호출 직후에 캐시를 갱신한다. 처음엔 "keyframe 도착마다"로 제안됐는데, 코드 확인 결과 densify_and_prune가 map() 안에서 호출되고 map()은 keyframe 도착 시뿐 아니라 background_polish_step/ idle_dense_map_step(유휴 시간에도 도는 별도 경로)에서도 불려서, keyframe 기준으로는 idle-time densify 구간에서 stale해질 수 있음을 확인 — 그래서 진짜 원인 지점에 직접 훅.

방향 기준점 — 셀 중심 고정

셀 좌표에서 바로 유도되는 고정값이라 계산 비용이 없다. 오차는 셀 크기(0.10m) 이내로 제한되고, 후보가 멀수록 그 오차가 만드는 각도 오차는 더 작아진다 — 근거리 후보에서만 미세하게 부정확할 수 있음.

저장 방식 — 이진 플래그

원본 nbv_gym도 최종 점수 산식에서 coverage_counts == 0 여부만 쓰고 실제 횟수는 안 쓴다(코드 확인함) — 이진(bool) 저장으로 정보 손실 없이 메모리만 아낀다.

방향 bin 개수 — G=64

COVER 원본/우리 스모크 테스트(test_cover.py)에서 이미 검증한 값 그대로 시작. 특별한 문제(각도 판별력 부족 등)가 보이기 전까진 바꿀 이유 없음.

문제 B — active-set 확장 스케줄 vs 매 스텝 샘플링

설계 완료

nbv_gym은 "닫힌 데이터셋을 200 step마다 1장씩 unlock"하는 구조라 재점수화가 드물게(전체 26,000 step 중 130번) 일어나도 됐다. VIGS는 등록된 뷰가 등록 즉시 학습 가능하고, 매 스텝 "이미 가능한 후보들 중 뭘 뽑을까"를 결정해야 하는 데다 후보 풀 자체가 라이브 스트림으로 계속 열려 있다 — nbv_gym의 "확장 스케줄" 개념이 대응점이 없다. 대신 이미 만들어둔 weighted_mix의 뷰별 가중치 자리에, 문제 A에서 설계한 상시 버퍼에서 뽑은 점수를 꽂는다.

가중치 결합 — keyframe_weight × rank 정규화 novelty

raw novelty 점수를 그대로 keyframe_weight에 곱하면, 점수 분포가 좁게 뭉쳐있을 때(예: 0.4~0.7 사이에 다 몰림) 실제 샘플링 확률에 거의 차이를 못 만드는 희석 문제가 있다는 지적이 나와서 — rank 기반 정규화로 바꾼다. 매 배치마다 후보들을 novelty로 줄 세워서 1위(가장 novel)→1.0, 꼴찝(가장 redundant)→0.1 같은 고정 범위로 선형 매핑한 뒤 그 값을 keyframe_weight에 곱한다. raw 점수가 아무리 뭉쳐있어도 배치 안에서 항상 최대/최소 10배 차이가 보장된다. keyframe 클래스 사전(exp66 dense_geom/weighted_mix에서 검증된, depth/normal loss 접근권 차이)은 그대로 유지.

왜 결정적 top-K가 아니라 확률적 샘플링인가 — nbv_gym은 점수 최상위 K개를 영구적으로 뽑아 세트에 편입시키는 결정적 방식이다. 우리 coverage 점수는 근사치 (frustum-only, occlusion 무시, 0.10m 셀)라서, "redundant로 보이지만 실제론 아닌" 뷰를 완전히 배제하면 그 측정 오차가 그대로 학습 기회 박탈로 이어진다. 확률적 가중치는 순위가 낮은 뷰에도 항상 0이 아닌 확률을 남겨서 이 오차에 대한 헤지가 된다.

갱신 주기 — 실측 결과 매 스텝 호출도 가능 (당초 추정 정정)

당초 "렌더링 없는 순수 벡터 연산이니 사실상 무시 가능"이라고 FLOP만 계산해서 추정했는데, 틀렸다. 처음 구현(후보마다 Python 루프)을 실측하니 pool=200에서 112ms — 학습 스텝 하나(15~30ms)보다 컸다. 원인은 연산량이 아니라 후보 수만큼 반복되는 GPU 커널 launch 오버헤드(씬 크기 3,631~900,000 Gaussian 전 구간에서 비용이 거의 안 변함 — launch-bound라는 증거)였다.

후보 전체를 하나의 배치 텐서 연산으로 처리하도록 score()를 재작성 → 재실측하니 pool=200에서 2.5ms(45배 개선), 씬 크기와 무관하게 평평함(시야당 보이는 Gaussian 수가 실측상 씬 전체 크기에 비례하지 않고 고정 범위(177~1556개, 평균 554개)라서). update() ~0.5ms, refresh_gaussian_counts()는 90만 Gaussian에서도 ~0.5ms. 학습 스텝 대비 score() 비중이 8~17%라 매 스텝 호출도 실시간 예산 안에 들어온다 — K-step 배치가 "필요조건"이 아니라 순수 선택지가 됨. 기본값은 그래도 K-step 배치로 유지(단순함), per-step 전환은 설정값 하나로 가능하게 구조만 잡아둠.

후보 풀 범위 — weighted_mix도 문제 A와 동일한 최근 N개로 통일

지금 weighted_mix는 등록된 keyframe+dense 뷰 전체를 후보로 쓰는데, 이걸 문제 A의 채점 윈도우(최근 N=200)와 동일하게 좁힌다. 채점 대상과 샘플링 대상이 항상 일치해서 "점수 없는 후보를 어떻게 처리할지" 같은 별도 로직이 필요 없다. 알려진 단점: 아주 오래전에 등록됐지만 윈도우 밖으로 밀려난 뷰는 재학습 기회를 영영 못 얻는다 — VIGS의 실제 후보 등록/소멸 패턴을 보고 실제 위험도인지 후속 확인 필요 (문제 A의 슬라이딩 윈도우 결정 때 남겨둔 것과 같은 후속 과제).

Cold-start 전환 — IMU 초기화 시점에 즉시 전환

IMU_initialized=False 구간은 기존 flat keyframe_weight만 쓰고, True로 바뀌는 순간부터 keyframe_weight × rank-novelty로 전환한다. if문 하나, 별도 상태 불필요 — 버퍼 자체가 그 시점부터 빈 상태로 시작하도록 이미 설계했으니 자연스럽게 맞아떨어진다.

구현 & 검증 — 독립 모듈, 실제 데이터로 관찰자 모드 검증

1차 검증 통과

설계를 코드로 옮긴 첫 단계. VIGS를 전혀 건드리지 않고 (1) 완전 독립된 단일 파일 모듈로 구현 → 합성 데이터로 단위 검증 → (2) 동료가 만든 aria-online-3dgs-bench(SLAM 분리, chunk-tree 기반 순수 incremental 3DGS 매퍼)의 train_incremental.py에 관찰자 훅만 붙여서 실제 aria1253 chunk-tree 데이터로 검증했다. 학습 동작 자체(random.choice(pooled_cams))는 한 줄도 안 건드림 — 결과에 전혀 영향 없이 버퍼만 옆에서 관찰.

모듈: scripts/incremental/coverage_buffer.py

문제 A의 9개 결정을 그대로 코드로 옮긴 SparseCoverageBuffer 클래스. torch 외 의존성 없음, 프로젝트 특정 import 없음 — 나중에 VIGS-SLAM gs_backend.py에 파일 하나만 복사해서 쓸 수 있게 설계. 합성 데이터 단위 테스트 6개(희소 할당, novelty 랭킹, diminishing returns, 캐싱 없는 라이브 재계산, Gaussian 개수 가중치, refresh가 새 행을 안 만드는 것) 전부 통과.

실데이터 검증에서 잡은 버그 — 예외를 던지면 안 됐다

real chunk-tree(aria1253, OKVIS2 기반)로 첫 실행 시 즉시 크래시 — 원인은 SLAM 포인트클라우드 자체의 삼각측량 이상치(정상 씬 스케일은 수 미터인데 한 점이 -285,640m)였다. 처음엔 셀 좌표가 범위를 벗어나면 ValueError를 던지게 짰는데, 이게 설계 실수였다 — coverage 버퍼는 보조 진단 시스템이지 메인 학습 경로가 아니므로, 실제 데이터에 흔한 이상치 한두 개 때문에 학습 전체가 죽으면 안 된다. 범위 밖 포인트는 조용히(1회만 경고 로그) 걸러내도록 수정.

real densify/prune 7회 통과 — 문제 A의 핵심 가설 실증

chunks_okvis_1253_g1(real OKVIS2 포즈, 256², 20 events, 1200 iteration)로 돌려서 실제 densify_and_prune가 7번 발동(Gaussian 수 184 → 3631)하는 동안 크래시 없이 버퍼가 계속 자랐다(178 → 7,310 cells). 이게 이 설계 전체의 핵심 주장 — "Gaussian 단위 장부는 densify/prune에 취약하지만 셀 단위는 안 그렇다" — 을 합성 데이터가 아니라 실제 SLAM+3DGS 파이프라인에서 실증한 것.

관찰 결과: rank 정규화의 알려진 부작용 하나 확인

후보 pool이 다양해진 뒤(event 3+, 100개 이상 서로 다른 뷰)에는 점수가 0.1~1.0 전 구간에 걸쳐 의미 있게 분포(1200개 기록 중 바닥/천장 쏠림 51/388개, 나머지는 스프레드). 다만 pool이 아직 좁을 때(초반 event, 사실상 같은 뷰만 반복 채점)는 부동소수점 수준의 의미 없는 차이까지 rank 정규화가 전체 범위로 늘려버려 점수가 요동치는 현상을 관찰함 — 실제 통합에서는 후보 풀이 항상 충분히 다양하므로 문제될 가능성은 낮아 보이지만, 근거 없는 가정이라 명시해둔다. 후속 확인 후보.

성능 실측 & 수정 — score() 45배 개선 (자세한 내용은 문제 B 갱신 주기 항목)

"실시간 가능한가"라는 질문에 실측으로 답했다: 최초 구현(후보마다 Python 루프)은 pool=200에서 112ms — 학습 스텝 하나(15~30ms)보다 컸다. 후보 전체를 배치 텐서 연산 하나로 처리하도록 score()를 재작성해 2.5ms로 개선(45배), 씬 크기 3,631~900,000 Gaussian 전 구간에서 비용이 평평함을 확인. 벤치마크 스크립트: scripts/incremental/exp66_cover_observer/(관찰자 스크립트와 함께 보관).

실데이터에서 잡은 버그 2 — 호스트마다 다른 visibility 컨벤션

벡터화 직후 재검증에서 또 크래시 — 이번엔 3dgs-custom의 render_pkg["visibility_filter"]가 표준 bool mask가 아니라 (radii > 0).nonzero() — shape이 [Nv]가 아니라 [Nv,1]인 인덱스 텐서였다. 이걸로 gaussians._xyz[visibility_filter]를 하면 [Nv,1,3]이 나와서 버퍼가 기대하는 [Nv,3]과 안 맞았음 — 원본 학습 코드는 이 shape에 맞춰 일관되게 쓰고 있어 문제가 없었을 뿐. 관찰 스크립트에서 학습 로직은 그대로 두고 별도로 radii > 0 bool mask를 만들어 쓰도록 수정. 재발 방지로 coverage_buffer.py 공개 API (update/score/refresh_gaussian_counts) 전부에 입력 shape 검증을 추가해, 다음에 다른 호스트(VIGS 등)에 이식할 때 같은 실수를 하면 모호한 인덱싱 에러 대신 원인을 바로 알려주는 에러가 뜨게 했다. 이식할 호스트마다 visibility 컨벤션을 확인해야 한다는 게 일반화된 교훈.

덤으로 하나 더 — .detach()는 복사가 아니다

같은 수정 김에: Gaussian 위치는 매 스텝 optimizer가 in-place로 갱신하는데, .detach()는 같은 storage를 보는 view일 뿐 복사가 아니다. 여러 스텝에 걸쳐 위치를 들고 있어야 하는 호출부(관찰 스크립트의 rolling pool 등)는 .detach().clone()을 써야 한다 — 안 그러면 저장해둔 값이 나중 스텝에서 조용히 바뀐다. 지금 버그를 일으키진 않았지만(관찰 스크립트가 그날그날 바로 소비하는 구조라), 실제 VIGS 이식 때 잊기 쉬운 지점이라 표시해둔다.
