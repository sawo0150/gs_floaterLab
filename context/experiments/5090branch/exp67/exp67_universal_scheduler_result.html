EXP67 · UNIVERSAL MAP SCHEDULER · STRICT CAUSAL STREAM · 2026-08-26

scene별 튜닝 없이 하나의 map()-only scheduler로 세 장면 검증

Stage B–F의 view-set·순서·batch 실험을 실제 VIGS tracking→mapping 경로에 통합했다. 최종 정책은 scene 이름, fps, 절대 frame 경계, 최종 길이, validation gradient를 보지 않는다. background_polish_step()은 금지하고 모든 최적화를 GSBackEnd.map() 안에서 수행한다.

결론 — 현재 실험 범위에서 채택할 공통안이다. 동일한 설정으로 aria1253, aria301_305, aria301_12F 모두 fixed-eval에서 PSNR·SSIM이 상승하고 LPIPS가 감소했다. fixed-eval PSNR 변화는 각각 +3.09 dB, +3.97 dB, +0.62 dB다. 12F의 PSNR 이득은 작고 반복 분산이 있으므로 “모든 장면에서 큰 폭 향상”이라고 말할 수는 없지만, perceptual 지표까지 포함한 개선 방향은 세 장면에서 일관된다. 이 설정은 절대적 전역 최적값이 아니라 지금 비교한 정책 중 다중-scene 증거를 통과한 가장 강한 단일 정책이다.

1. 절대 불변조건: scene에 따라 바뀌는 것은 입력뿐

공통으로 고정
  • tracking: window 15, radius 2, motion filter 2.6, frontend iteration 2/0
  • replay: RGB-only, B1, batch 1, seed 0, shuffle-without-replacement
  • view-set: temporal maximin + service-credit water filling
  • phase: topology·capacity·실제 service pressure 기반 상태전이
  • PGBA recovery, deadline guard, fixed-eval 분리 규칙
scene별로 허용되는 차이
  • RGB/IMU/calibration 입력 경로
  • 평가할 입력 span(--length)
  • 그 입력에서 자연스럽게 관측되는 keyframe·PGBA·idle 시간

실행 스크립트는 --length N 외 추가 인자를 거부한다. 따라서 scene별 learning rate, frame gate, stride, iteration override를 넣을 수 없다.

aria1253은 기존 exp66과 직접 비교하기 위해 첫 1,253 frame span을 사용했다. 이것은 scheduler phase 경계가 아니라 평가 입력 범위다.

2. 최종 pipeline

1 · causal 입력
RGB/IMU와 tracked KF 도착
→
2 · view-set membership
KF 사이 후보를 maximin 순으로 두고 service가 지불한 만큼 편입
→
3 · optimizer order
성숙한 causal pool을 동적 shuffled epoch로 1회씩 기회 부여

핵심은 view-set 선택과 학습 순서를 분리한 것이다. novelty는 “어떤 view를 pool에 넣을지”에만 쓰고, optimizer 순서는 novelty/residual 우선이 아니라 shuffle이다. 이 분리가 Fisher novelty-first 실패와 Stage C의 shuffle 우세를 동시에 반영한다.

3. 수학적 모델

3.1 view-set: coverage 후보를 budget이 감당할 만큼만

두 tracked keyframe 사이 interval을 j, 이미 고른 endpoint와 dense view 집합을 A_j라 한다. 후보의 편입 우선순위는 1차원 farthest-point cover다.

v* = arg max[v in interval j] min[a in A_j] |frame(v) - frame(a)| r = 2 # 새 view가 받아야 할 최소 반복 기회 q_t = floor(service_credit_t / r) # 현재 추가 가능한 view 수 j* = arg min[j with pending views] m_j # 가장 덜 채워진 interval부터 water-fill
  • 각 새 KF interval은 deadlock을 막기 위해 가장 novel한 view 하나를 bootstrap한다.
  • 나머지는 기존 active pool이 성숙했고 실제 replay step이 쌓인 경우에만 편입한다.
  • credit 2는 “한 번 봄”과 “같은 view의 다음 관측에서 progress를 확인할 최소 반복”을 구분하는 evidence count다. fps나 scene scale이 아니다.
  • interval별 편입 수 m_j가 작은 곳부터 채워, 한 구간에 dense view가 몰리지 않게 한다.

3.2 순서: 동적으로 자라는 shuffle-without-replacement

π_e = UniformPermutation(active causal views at epoch e) new arrival v → insert v at a uniformly random unfinished-epoch position each active view receives at most one draw before the next refill

“가장 novel/residual이 큰 view를 계속 먼저” 주지 않는다. 새 view도 곧 기회를 받지만 매번 앞을 가로채지 못한다. 이것이 coverage와 gradient 상쇄/정렬을 함께 만족시키는 가장 단순하고 실측상 강한 기본값이었다.

3.3 topology와 replay의 phase certificate

FRONTIER └─ topology event ≥ 2 and current Gaussian count ≥ latest pre-prune capacity → BALANCED normal frontier iters = min(requested, round(sqrt(window size))) └─ two complete shuffled opportunity passes → REPLAY (ordinary frontier optimizer iters = 0)

절대 frame에서 “이제 replay”라고 전환하지 않는다. 두 번의 독립 topology 관측, 마지막 prune 이전 capacity 회복, 두 번의 causal pool pass라는 상태 증거만 사용한다.

3.4 idle이 사라지는 고-KF stream: service-pressure feedback

z_t = 1 if no replay update was actually serviced since previous dispatch or another mapping packet is pending if z_t is repeated twice and topology evidence exists: (frontier iters, replay iters) = (0, requested iters) else: use the normal phase allocation

여기서 중요한 단어는 대체다. replay iteration을 기존 작업 위에 더하지 않고, packet이 이미 갖고 있던 optimizer budget을 동일 개수의 one-view B1 replay로 바꾼다. aria301_12F에서 “queue가 비었으니 idle”이라고 판단하면 tracking이 GPU를 계속 점유하는 상황을 놓쳐 replay가 0회가 됐다. 실제 service 유무를 피드백하자 이 실패가 해소됐다.

3.5 PGBA와 deadline

  • PGBA pose revision 뒤에는 topology를 다시 열지 않고 min(requested, round(sqrt(window)))의 bounded RGB recovery만 수행한다.
  • 이전 revision 이후 causal pool이 두 pass 성숙하기 전에는 다음 PGBA를 back-pressure한다.
  • 다음 RGB 도착 전 남은 시간이 최근 관측된 replay step의 보수적 최대 비용보다 작으면 새 replay step을 시작하지 않는다.

4. Fisher/gradient 신호를 최종 online score로 쓰지 않은 이유

Fisher novelty는 view-set coverage의 동기지만 optimizer 순서의 충분조건은 아니다. 새로운 eigen-direction을 계속 보강하면 최소 고유값이나 식별 가능성은 좋아질 수 있지만, 현재 eval objective가 원하는 gradient와 정렬되지 않으면 초반 loss 감소는 느려질 수 있다. 실제 Stage C에서 novelty-first와 residual-first가 shuffle보다 나빴다.
  • reference gradient는 후보마다 정렬을 probe하려면 반복 render/backward가 필요하고, incremental 환경에서 미래 validation을 정의하기도 어렵다.
  • Stage D/E의 counterfactual probe는 분석용으로 유용했지만, 그것을 online 의사결정 비용으로 지불할 근거는 충분하지 않았다.
  • 따라서 최종 controller는 validation/reference gradient를 전혀 보지 않고, coverage는 membership, 상쇄 가능한 반복 기회는 shuffle, 계산 배분은 causal service evidence로 분리했다.
  • Stage F의 blur/exposure/combined filter도 temporal baseline보다 AUC가 일관되게 낫지 않았다. 그래서 품질 gate를 추가해 scene 의존 threshold를 만드는 대신 제외했다.

10. strict 1.5× timing — 두 경계를 분리해 공개

ONLINE_LOOP_START는 reader process cold-start 약 3.4초를 포함한다. 실제 stream latency는 첫 RGB packet이 consumer에 도착한 시점부터 ONLINE_LOOP_DONE까지다.

입력 arrival은 sensor timestamp의 정확한 1.5×로 pace된다. 마지막 frame은 budget 끝에 도착하므로 그 packet을 소비하는 4–15 ms tail이 남았다(최대 약 0.009%). 따라서 “수학적으로 completion ≤ 1.5×”라고 쓰지 않고, 1.5× causal pacing + 한 final-packet tail로 보고한다. eval 시간은 이 표에 포함하지 않으며 eval 중 map update는 0이다.

13. 해석과 현재 한계

지금 말할 수 있는 것
  • scene별 frame gate 없이 실제 incremental pipeline에서 작동한다.
  • 세 scene 모두 fixed-eval PSNR/SSIM/LPIPS 방향이 개선됐다.
  • 1253·305에서는 개선 폭과 paired win이 크다.
  • 같은 feedback이 stream의 idle/pressure 차이에 적응한다.
아직 말할 수 없는 것
  • 세 scene·한 GPU 결과만으로 모든 scene의 전역 최적 설정이라 할 수 없다.
  • 12F의 PSNR 개선은 작고 PGBA 비동기 분산이 있다.
  • fixed set에 tracked-KF overlap이 있어 완전한 held-out validation은 아니다.
  • eval_metrics_only였으므로 사람의 side-by-side render 판독은 하지 않았다. 품질 개선 판단은 PSNR/SSIM/LPIPS와 paired frame 통계다.
  • 마지막-frame tail까지 포함한 exact hard deadline은 4–15 ms 초과했다.

따라서 다음 개선도 scene별 숫자 조정이 아니라 공통 rule이어야 한다. 우선순위는 PGBA 결정성/동기화, 마지막 packet deadline 정의, 그리고 새로운 scene을 사전 등록한 leave-one-scene-out 검증이다.
