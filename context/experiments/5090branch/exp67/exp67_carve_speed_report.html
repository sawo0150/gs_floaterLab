gs_floaterLab · exp67 · working note

splat-wise backward, depth loss vs carve loss 속도, 그리고 CPU→GPU maxop 패치

CaRtGS 논문의 "fast splat-wise backpropagation"이 실제로 빠른지 실측하고, 배치 carve loss(soft/force/gate/prune)와 depth loss(sparse_depth_prior)의 속도를 같은 하네스에서 비교한 뒤, carve의 CPU 병목 하나(maxop)를 GPU voxel 근사로 실제로 패치해서 다시 잰 기록.

2026-08-25 RTX 5070 Ti · conda env 3dgs 배치 3DGS train.py · ORB 03_rgb_3dgs_full

01 CaRtGS splat-wise backward — 실제로 빠른가

CaRtGS 저장소(cartgs-src/cuda_rasterizer)를 까보니 splat-wise backward(PerGaussianRenderCUDA, warp당 32-splat 버킷)와 원본 pixel-wise backward(renderCUDA)가 둘 다 코드에 있었음 — 후자는 죽은 코드. 런타임 env var로 토글하도록 패치해서 같은 forward/데이터로 A/B.

규모(N, 해상도)가 커질수록 speedup도 커짐 — atomic contention 완화라는 논문 주장과 방향 일치. 같은 시드로 gradient diff도 떠봤는데 means3D/opacities/scales/rotations/dc/shs 전부 abs diff ~1e-6~1e-5 수준(fp32 atomic-add 누적 순서 차이 수준) — 빠르지만 틀린 게 아니라 진짜 free lunch.

VIGS-SLAM 적용 가능성

실제 VIGS-SLAM map() 루프의 timing.jsonl을 집계해보니 backward가 전체 시간의 44.2%(loss_compute 45.4%, rasterize 7.8%) — 적용할 가치가 있는 크기. 다만 VIGS-SLAM 자체 rasterizer는 CaRtGS 스톡 커널보다 훨씬 커스텀됨: depth gradient가 이미 backward에 포함(renderCUDA<C, DEPTH=true>)되어 있고, Phase 8b의 멀티카메라 배치 backward(renderCUDA_batch, per-camera SE3 pose gradient 포함)까지 있어서 CaRtGS엔 없는 부분을 새로 설계해야 함 — 단순 포팅 아님, 미착수.

02 carve loss의 정체 — 4개 구성요소

VIGS-SLAM 온라인 carve(get_loss_carve_depth_violation)와는 다른, exp38~42 배치 트랙의 원조 carve loss(3dgs-custom/eval/carve_loss.py)를 조사. 챔피언 레시피(exp40b) 이름 그대로 4개.

왜 이렇게 차이 나나

depth(sparse_depth_prior)는 전부 GPU 텐서 연산 — view별 projection을 캐시해두고 재사용, CUDA 병렬성 그대로 사용. carve는 score 계산이 CPU numpy cKDTree / scipy.ndimage 기반이라 GPU-CPU 왕복이 매번 발생. "carve가 비싸다"는 알고리즘이 무거워서가 아니라 구현이 CPU-bound라서 — depth loss처럼 GPU로 옮기면 훨씬 싸질 여지가 있다는 뜻.

04 진짜 병목 찾기 — 두 번 틀리고 세 번째 맞음

"GPU로 옮기면 빨라진다"는 가설을 실제로 검증하는 과정에서 첫 두 시도가 틀렸음 — 그 과정 자체가 어디가 진짜 병목인지 알려줌.

시도 1 — 틀림

d5(SLAM anchor까지 5-NN)를 GPU로. anchor 7,190개 대상 CPU cKDTree.query(k=5)는 이미 22.4ms. GPU chunked cdist+topk로 바꿨더니 63ms — 오히려 느림 (anchor 수가 작아서 GPU 커널런치/전송 오버헤드가 이득을 못 봄). 여긴 손대지 않기로.

시도 2 — 진짜 병목 특정, 그런데 첫 "개선"도 틀림

코드 주석의 "~1-2초"는 사실 maxop(자기 자신 ball-query, "반경 내 최대 opacity")였음. 재현: cKDTree 빌드 40.9ms + query_ball_point 80.7ms + Python max-reduce 루프 219.4ms = 341.0ms 합계. 기존 필드의 voxel(0.10m)을 그대로 재사용해 own-cell-only로 GPU scatter-max 했더니 0.21ms(1658×)인데, 3×3×3으로 넓히면 개선될 거라 생각하고 해봤더니 오차가 20.2%→79.7%로 오히려 악화. voxel(0.10)이 radius(0.05)보다 이미 큰 상태에서 27칸으로 넓히면 검색 큐브가 반지름의 몇 배로 부풀어서 먼 점까지 다 "이웃"으로 잡음.

시도 3 — 맞음

칸을 넓히는 게 아니라 radius에 맞춰 더 잘게 쪼개야 함 (voxel ≈ radius/2). voxel=0.025 + 3×3×3 dilation: 1.13ms, CPU 대비 ~300×, 오차 0.1 이상 틀리는 비율 20.2%→5.6%.

05 실제 패치 — OOM 한 번 더

eval/carve_loss.py의 _refresh_score에 _gpu_maxop()를 추가해 CPU 블록을 대체. 첫 실전 테스트(soft+force+gate+prune 챔피언 config, 실제 densify 이벤트 포함)에서 즉시 OOM.

버그 — 793GB 할당 시도

grid 경계를 xyz.min()/max()로 매 호출마다 데이터에서 직접 뽑았더니, 실제 densify 이벤트에서 나온 outlier Gaussian(먼 곳으로 튄 split/clone) 때문에 voxel 개수가 폭발. 이번 세션 exp66 COVER 작업 때 coverage_buffer.py에서 이미 겪었던 것과 동일한 클래스의 버그 — 데이터 기반 bound는 outlier에 취약. carve가 이미 갖고 있는 camera-derived 고정 scene box(self._lo / self._dims)를 재사용하고, 그 밖은 maxop=0으로 처리하도록 수정해서 해결.

07 남은 것

  • 미착수 force 전용 _refresh_phi의 scipy.ndimage.distance_transform_edt — 여전히 CPU-bound. force가 여전히 제일 비싼(+48.9%) 이유가 이것. jump-flooding류 근사 GPU EDT가 후보지만 아직 벤치마크 안 함.
  • 미착수 VIGS-SLAM 온라인 루프로의 이식 — depth gradient 포함 + 멀티카메라 배치 backward까지 있는 VIGS-SLAM 자체 rasterizer에 CaRtGS splat-wise backward를 넣으려면 새로 설계 필요.
  • 열린 질문 carve의 CPU-bound 비용이 배치(오프라인) 환경에서는 "그냥 느림"이지만, VIGS-SLAM처럼 keyframe당 tight real-time budget이 있는 온라인 환경에서는 상대적으로 훨씬 아플 수 있음 — 아직 온라인 환경에서 측정 안 됨.
