1. 판정 정정

정정기존 결과 보고서의 floater PASS는 manual region 안에서 opacity > 0.3인 Gaussian 중심 개수에만 해당한다. PLY 전체 geometry, 저-opacity dust, covariance footprint, 큰-scale Gaussian까지 baseline과 동등하다는 의미로 읽으면 안 된다.

2. 출발점 — dense 수렴과 geometry supervision

exp67 scheduler는 dense RGB replay로 photometric 수렴을 크게 높였다. Dense action은 RGB-only지만 xyz·rotation·scale·opacity·color를 제한하지 않는다. Keyframe action은 RGBD+normal로 같은 전체 파라미터를 갱신한다. dense 비율이 높아지면서 depth/normal의 상대 서비스 빈도가 줄었고 native keyframe baseline보다 floater가 증가했다.

7. 신호가 action까지 가지 못한 원인

  1. Self max-opacity protection: 주변 최대 opacity 계산에 자기 자신이 포함되어 opacity≥.5 Gaussian은 strict score>.5를 구조적으로 통과하기 어렵다.
  2. Fisher hard gate: 단방향 trajectory의 유효 free-space 후보도 제거했다. low-opacity 후보에서 156 / 836개가 추가 탈락했다.
  3. Center-only score: 중심 밖의 큰 covariance free-space 침범을 검출하지 못했다.
  4. Newborn cache zero: 같은 evidence generation에서 태어난 Gaussian은 다음 refresh까지 score 0이었다.
  5. 약한 실제 action: 최종 selected 약 601/624개, prox 3회, hard/gate prune 0개였다.
  6. 후반 garbage collection 부재: replay가 native densify/prune clock을 진행하지 않아 opacity가 낮아져도 PLY에서 삭제되지 않았다.

8. Power-of-two refresh의 이유와 한계

Score가 지수함수인 것이 아니라 전체 재계산 시점을 2,4,8,… packet에 둔 것이다. 매 keyframe 전체 Gaussian을 재계산하면:

1 + 2 + 3 + ... + n = O(n^2)

Power-of-two rebuild의 누적 비용은:

1 + 2 + 4 + ... + n < 2n = O(n)

하지만 최신 evidence latency가 커졌다. 97/123 packet run에서 generation 7, refresh 6회였고 64 이후 ray는 raw dictionary에 저장돼도 128 generation 전까지 Gaussian score에 반영되지 않았다. 후반 full refresh 한 번은 약 379–579ms였다.

305에서 anchor를 약 21,090→134,290으로 6.4배 늘린 variant도 raw AUC만 일부 개선했고 visible floater는 576→579, replay step은 15,139→14,150이었다. 더 많은 ray만으로는 해결되지 않는다.

9. 추가 감사 — viewset maturity가 실제로 budget을 제어했는가

후속 코드·로그 감사에서 MAP_VIEWSET_ADMISSION이 계속 출력된다는 사실을 “큰 pool이 keyframe 사이에 두 epoch씩 재성숙했다”로 해석하면 안 된다는 점을 확인했다. 현재 controller에는 서로 다른 두 admission 경로가 있다.

  1. Bootstrap admission: 새 keyframe interval마다 대표 dense view 1장을 mature=False여도 무조건 추가한다.
  2. Budget admission: 기존 active dense view의 누적 selection count 최솟값이 required_opportunities=2 이상일 때만 pending view를 추가한다.

따라서 후반의 added=1/2 로그는 대부분 budget이 아니라 새 interval의 bootstrap이었다. 로그 줄 간격은 replay draw 수나 epoch 완료를 나타내지 않는다.

aria1253의 budget admission은 active 83개가 mature했던 한 이벤트에서 207장을 한꺼번에 추가한 뒤 끝까지 멈췄다. 305도 +90, +168, +193, +222장의 네 burst로 발생했다. 즉 현재 동작은 부드러운 water-filling이 아니라 unconditional bootstrap + rare large burst + long stall에 가깝다.

추가 정정: 새 view가 count 2에 도달하는 데 정확히 2 × pool draw가 “최소”로 필요한 것은 아니다. 과거 view의 count와 현재 queue 위치에 따라 달라진다. 그러나 큰 신규 cohort가 shuffle-without-replacement에서 모두 두 번 선택되기까지 필요한 시간이 pool 크기에 대해 선형으로 증가한다는 구조적 우려는 맞다.

9.1 기존 endpoint/stability 설정은 pool-size 안전장치가 아니다

  • causal_endpoint_distance=min(alpha,1-alpha)의 범위는 [0,.5]이고 threshold가 .5라 모든 dense view가 통과한다.
  • Threshold를 낮춰도 매 interval의 endpoint 근처 view가 계속 누적되므로 장기 pool을 유한하게 만들지는 못한다.
  • stability_lag=0은 지연도 없고, 양수로 바꿔도 최근 view를 늦출 뿐 과거 pool을 줄이지 않는다.
  • 최종 run의 background_polish_max_pool_size=null이므로 hard capacity도 없었다.
  • Mixed replay의 실제 shuffle queue에는 dense뿐 아니라 keyframe도 들어가지만 maturity snapshot의 minimum은 dense만 검사한다.

Archive는 영구 폐기 장소가 아니라 현재 epoch에서 빠져 있는 성숙 view 저장소다. Archive 전체를 다시 epoch에 넣으면 원래의 무한 pool 문제가 재발하므로, 매 epoch에는 제한된 rehearsal quota만 active로 복귀시킨다.

Active_(e+1) = UnderServed_new ∪ Geometry_keyframes ∪ SmallSample(Archive) |Active_t| ≤ P_capacity(t)

P_capacity(t)는 장면별 고정 fps나 frame 번호가 아니라 측정된 replay 처리량과 허용 service latency로 정한다. replay 처리량을 μt draws/s, service horizon을 Ht, 필요한 반복을 r이라 하면 기본 제약은 다음과 같다.

r · |Active_t| ≤ mu_t · H_t
  • 새 interval의 bootstrap도 active capacity가 있을 때만 넣고, 없으면 pending에 두거나 성숙·중복 view와 교체한다.
  • required_opportunities=2는 학습 완료가 아니라 최소 노출 조건이다. 두 번 봤다는 이유만으로 영구 archive하지 않는다.
  • 새 view, geometry keyframe, archive rehearsal의 membership을 정한 뒤 active 내부 optimizer 순서는 계속 shuffle한다.
  • Global minimum 하나보다 admission 이후 부족 기회량을 합친 service debt를 추적한다.
D_t = sum_(v in Active_t) max(0, r - c_v_since_admission)

이 분리는 view membership/coverage와 optimizer order를 다시 섞지 않으면서 epoch 길이를 처리 가능한 범위로 유지한다. 또한 증분 carve가 추가되며 replay step 비용이 변해도 실제 처리량 μt를 통해 active capacity에 반영할 수 있다.

9.3 Archive를 추가한다는 말의 정확한 의미

맞다. 핵심 목적은 shuffle epoch가 돌아야 하는 working active pool의 크기를 유한하게 유지하는 것이다. 다만 전체 view를 단순히 active/archive 두 덩어리로 한 번 나누고 고정하는 구조는 아니다. 새 view가 들어오면 아직 최소 기회를 받지 못한 view를 active에 우선 배치하고, 이미 기회를 받은 view는 archive로 내린다. 이후 archive에서도 작은 rehearsal 표본을 매 epoch 다시 뽑아 망각을 막는다. 따라서 전체 학습 데이터는 계속 보존되지만, 한 epoch의 길이만 처리 가능한 크기로 제한된다.

All arrived views = Pending ∪ Active ∪ Archive epoch length = |Active| ≤ P_capacity(t) Active_(e+1) = under-served/new views ∪ required geometry keyframes ∪ bounded rehearsal sample from Archive

이 구조가 해결하는 것은 스트림 길이가 늘수록 한 epoch가 무한히 길어지고 새 view의 두 번째 기회가 늦어지는 문제다. 반대로 archive 자체가 view의 학습 완료를 보장하거나, 어떤 view가 좋은지를 판정하거나, optimizer 순서를 novelty-first로 바꾸지는 않는다. Membership은 capacity·최소 service·rehearsal로 정하고, 선택된 active 내부 순서는 Stage C 결과대로 shuffle-without-replacement를 유지한다.

실측과 구조적 위험을 구분해야 한다. exp66–68의 수백-view, strict 1.5× 구간에서는 keyframe 사이 GPU replay 처리량이 충분해 admission 간격 증가가 겉으로 드러나지 않았다. 그러나 endpoint threshold=.5와 stability_lag=0은 실제 pool 제한이 아니므로, 수천 view의 긴 스트림·비싼 carve/Fisher·더 빡빡한 pacing에서는 같은 구조가 다시 병목이 될 수 있다. 따라서 “지금 로그에서 stall이 작았다”는 사실은 bounded pool이 불필요하다는 근거가 아니라, 아직 처리량 한계를 넘지 않았다는 뜻이다.

Capacity는 scene별 fps나 frame index로 하드코딩하지 않고, 실제 ordinary replay step 시간 ĉstep과 다음 keyframe까지의 sensor-time horizon Ĥ로 계산한다.

P_capacity(t) = floor(H_hat / (r · c_hat_step)) r = required_opportunities

희귀한 전체 carve refresh는 실제 deadline budget에는 포함되지만 ordinary replay 단가 추정에서는 분리한다. 그렇지 않으면 한 번의 O(N) maintenance가 이후의 모든 짧은 RGB replay를 과도하게 막기 때문이다. 다만 maintenance가 자주 발생한다면 별도의 maintenance reserve를 두어야 하며, 이 항목은 장기 스트레스 테스트 대상이다.

12. Floater 제거 — opacity와 pruning의 역할

Opacity 억제만으로는 PLY에 dust가 남고 memory/render 비용도 줄지 않는다. 반대로 carve score만으로 즉시 삭제하면 tracking noise로 정상 surface를 훼손할 수 있다.

  • Opacity logit 감소는 이후 RGB evidence로 회복 가능한 reversible 완충 단계다.
  • 여러 independent keyframe에서 모순이 반복되고 terminal evidence가 약할 때 hard prune한다.
  • 성숙한 free-space field 안의 newborn은 높은 confidence에서 즉시 gate할 수 있다.
  • 후반 native topology clock과 무관한 mature garbage-collection event가 필요하다.

요약: carve는 삭제 후보와 confidence를 결정하고 opacity는 완충 장치로 사용한다. 충분히 확실해진 dust는 최종적으로 반드시 pruning한다.

13.1 이번 loop에서 고정한 판정법

  • 1253·305 photometric floor: fixed held-out PSNR 27 dB 이상이면 충분한 것으로 판정한다. 최고 PSNR을 다시 맞추기 위한 파라미터 탐색은 하지 않는다.
  • 12F: 기존 exp67 ceiling이 약 26.4–26.6 dB였으므로 절대 27 dB를 강제하지 않고, 기존 범용 scheduler 대비 품질·시간의 상대 보존으로 판정한다.
  • Geometry label: 학습과 설정 선택에 사용하지 않고 run이 끝난 뒤에만 평가한다. 1253/305 manual mask에 맞춘 threshold sweep을 금지한다.
  • 설정 동결: 장면 이름·frame index·특정 시점을 조건으로 한 분기를 두지 않는다. 같은 CLI와 같은 controller가 세 장면을 처리해야 한다.
  • Streaming: 모든 update는 GSBackEnd.map() 안에서만 수행하며 background_polish_step과 post-stream refinement는 금지한다.

유지: dense RGB unrestricted geometry, keyframe RGBD+normal, shuffled order, global 3D carve 문제 분해, Fisher를 geometry confidence로 쓰는 방향.

폐기·수정: opacity>.3 center-only PASS, self max-opacity protection, Fisher hard gate, power-of-two-only refresh, newborn zero cache, center-only score, 후반 prune 부재.

구현 목표: pending/bounded-active/archive로 replay epoch를 처리 가능한 크기로 유지하면서, 모든 도착 keyframe의 depth ray를 causal하게 누적하고 변경 voxel과 겹치는 Gaussian support만 증분 재채점한다. 그 뒤 soft opacity → reversible prox → mature pruning으로 dust와 큰-scale floater를 실제 제거한다. 이 설계는 아래 §14에서 구현·검증했다.

다음 연구 단위: scheduler membership/order는 exp67의 검증된 bounded shuffle을 기준선으로 고정하고, carve는 먼저 action 없이 detector telemetry만 켠 동일-trajectory paired run으로 분리한다. 그 다음 detector recall, action dose, photometric gradient 충돌을 각각 독립적으로 검증해야 한다. 이번 loop에서 추가 숫자 tuning을 하지 않은 이유도 이 분해가 선행돼야 하기 때문이다.

15. 후속 감사 — 왜 low-opacity dust는 삭제되지 않았나

결론: opacity를 낮추는 경로는 작동했지만, 낮아진 Gaussian을 최종 회수하는 garbage collection clock이 사실상 작동하지 않았다. 현재 구조에서 low opacity는 prune의 충분조건이 아니다.

15.1 Native prune은 조건보다 실행 기회가 부족했다

사후 지표의 dust는 opacity ≤ .1이다. 저장된 mapping config의 gaussian_th=.7보다 낮으므로 opacity 항만 보면 native prune 대상이다. 그러나 densify_and_prune()은 frontier의 topology event에서만 호출된다.

update_gaussian = advance_iteration_count AND NOT replay_iteration AND iteration_count mod 150 = 50
  • 수천 번의 dense/keyframe replay는 의도적으로 native topology cadence를 진행하지 않는다.
  • postmortem run의 native topology event는 2회뿐이었다. 마지막 event 뒤 opacity가 낮아진 row는 삭제 기회를 받지 못했다.
  • Native mask는 최신 keyframe lineage를 일시적으로 제외한다: unique_kfIDs != max(unique_kfIDs).
  • gaussian_reset=2,000,000,001이므로 주기적 opacity reset/cleanup도 사실상 비활성이다.

15.2 Causal carve prune은 일반적인 low-opacity GC가 아니다

Carve hard prune은 opacity가 낮다는 이유만으로 실행되지 않는다. 다음 조건을 동시에 요구한다.

eligible(g) = [carve_score(g) > .5] AND [persistence(g) ≥ ceil(2 · (2 - FisherQuality(g)))] AND [opacity(g) ≤ .1 OR contribution(g) ≤ .1 · median] AND [cumulative contribution budget ≤ .005]

즉 동일 Gaussian이 여러 독립 field generation에서 다시 score되어야 한다. 12F pressure mode에서는 한 refresh의 row budget이 2,048에서 약 46으로 줄었고, 많은 row가 재채점 대기 상태로 남아 persistence가 성숙하지 못했다.

표의 persistence 통과 9/5개는 저장 직전 마지막 diagnostic snapshot의 값이다. 해당 row가 성숙했을 때 새로운 prune action generation이 다시 열렸다는 뜻은 아니므로, 실행 로그의 budget_pruned=0과 모순되지 않는다.

15.3 Opacity prox는 dust를 약하게 만들지만 PLY에서 제거하지 않는다

Reversible prox와 soft gradient는 opacity logit만 낮춘다. RGB evidence가 돌아오면 회복할 수 있다는 장점이 있지만, xyz·scale·rotation과 optimizer state는 그대로 남는다. 따라서 큰 가시 floater를 흐리게 만드는 동시에 opacity≤.1 dust band의 개수를 유지하거나 늘릴 수 있다.

필요한 수정: densification과 분리된 mature GC event가 필요하다. 단순 opacity<threshold 즉시 삭제가 아니라 충분한 나이 + 낮은 opacity + 낮은 실제 render contribution을 만족한 row를 measured maintenance budget 안에서 회수해야 한다. Carve persistence는 free-space 확신을 더하는 보조 조건으로 쓴다.

16. 후속 감사 — 12F PSNR은 왜 21.08 dB까지 떨어졌나

주원인은 hard pruning이 아니다. 12F의 budget_pruned=0이었다. 병목은 carve maintenance가 photometric update budget을 대체한 것과, 충분히 갱신되지 않은 carve cache로 opacity/xyz gradient를 반복 적용한 것이다.

v1z는 keyframe 438회, dense RGB 1,718회만 갱신했다. exp67보다 전체 photometric update가 약 57–61% 감소했다. “dense view가 많을수록 빨리 수렴한다”는 exp66/67의 가장 강한 이득을 carve 계산이 다시 빼앗은 셈이다.

16.2 12F는 원래 idle 여유가 거의 없는 포화 장면이다

exp67에서 12F는 worker-pressure 관측 256회 중 227회, 약 89%에서 기존 frontier budget을 replay로 교체해야 했다. 305처럼 idle GPU 시간이 넉넉한 장면이 아니다. 여기에 v1z는 다음 비용을 추가했다.

  • 275개 keyframe-depth packet의 누적 3D field.
  • incremental score refresh 약 28.7초.
  • 152,517 support ID와 35,439 dirty key.
  • strict sensor budget 165초 대비 tracking loop 약 181초.

따라서 carve는 “남는 시간에 수행된 무료 regularization”이 아니라, 12F에서는 photometric replay를 직접 대체하고 tracking/mapping deadline까지 밀어낸 작업이다.

16.3 계산을 줄인 v1z에서는 score 신선도도 함께 나빠졌다

pressure-aware refresh는 12F 시간을 v1w의 약 203초에서 181초로 줄였다. 하지만 종료 시 pending_score_ids=142,300으로 support ID의 약 93.3%가 재채점을 기다렸다. pending은 반드시 score 0이라는 뜻은 아니지만, 최신 field/topology에 대해 stale할 수 있다는 뜻이다.

  • 최종 score>.5 row는 17,106개, 마지막 selected row는 15,055개였다.
  • soft opacity gradient와 lambda_force=.05 xyz attraction은 map step마다 현재 cache에 반복 적용됐다.
  • newborn gate 2,461개, opacity prox 6,365 row가 적용됐지만 일반 hard prune은 0개였다.

즉 v1z는 계산량은 줄였지만, 일부 row에만 새 evidence가 반영되는 비대칭·비정상적인 regularizer가 됐다. 이 gradient가 RGB가 원하는 방향과 충돌했을 가능성이 높다. 다만 정확한 기여도는 carve telemetry-only / action-only paired 실험 전에는 분리할 수 없으므로, 단독 인과로 단정하지 않는다.

28.7s carve maintenance → photometric steps 5,026–5,587 → 2,156 + stale / partial carve gradient + 16s deadline overrun → fixed-eval PSNR 26.41 → 21.08 dB
