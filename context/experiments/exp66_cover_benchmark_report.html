exp66 부속 — COVER (CVPR 2026) 레퍼런스 구현 벤치마크

COVER의 뷰 선택이 실제로 수렴을 빠르게 하는가

Chen et al., "Coverage Optimization for Camera View Selection" (CVPR 2026)의 공식 구현 chengine/nbv_gym을 그대로 클론해 aria1253 씬에서 README 예시 커맨드로 학습을 돌렸다. coverage 지표 기반 뷰 선택 vs random 뷰 선택을 동일한 progressive 스케줄로 26,000 step 학습해 비교.

결론

step 기준으로는 COVER가 이긴다 (28.54dB vs 27.47dB, +1.07dB) — 하지만 같은 결과를 얻기까지 실제 시계(wall-clock)로는 2.9배 느리다 (52분 vs 18분). random이 26,000 step을 다 마친 시점(18분)에 coverage는 겨우 8,000 step, 22.46dB에 머물러 있었다 — 같은 시간 예산이면 random이 5dB 가까이 앞선다. 우리 프로젝트의 실시간 제약을 그대로 적용하면, 이 레퍼런스 구현 형태로는 COVER를 incremental 파이프라인에 이식할 이유가 없다.

왜 이렇게 느린가

원인은 알고리즘이 아니라 구현이다. nbv_gym/view_selector.py가 뷰를 한 장 추가할 때마다 model.update_view_attributes(training_cameras)를 호출하는데, 이 함수는 그동안 활성화된 모든 뷰를 처음부터 다시 렌더링해서 coverage histogram을 통째로 재계산한다 (reset_view_attributes=True가 기본값 — 새로 추가된 뷰 하나만 반영하는 증분 업데이트가 아니다). 비용은 O(활성 뷰 수 × Gaussian 수)이고, 학습이 진행될수록 활성 뷰도 Gaussian도 계속 늘어나므로 재계산 비용이 계속 불어난다.

처음엔 --pipeline.add-every-n-steps 20으로 돌렸다가(후보 pool 1042장을 26,000 step 안에 다 훑게 하려고 임의로 낮춘 값) coverage의 ETA가 5~7시간대로 치솟는 것을 보고서야 문제를 발견했다. nbv_gym 파이프라인 기본값은 1000, README 예시는 200 — README 기본값(200)으로 되돌리자 정상 페이스로 돌아왔다. 이 리포트의 수치는 모두 재시작한 200-step 스케줄 기준이다. 재계산 빈도가 10배 줄어든 뒤에도 coverage는 random보다 여전히 2.9배 느렸다 — add_every_n_steps 설정 문제가 아니라 전량 재계산이라는 구조 자체의 비용이라는 뜻이다.

읽는 법

  • step 곡선의 역전 구간 — coverage는 step 0~12,000 구간에서는 오히려 random보다 낮다(최대 −0.5dB). step ≈13,000 부근에서 역전해 이후 격차가 계속 벌어져 26,000 step에서 +1.07dB로 마감한다. COVER가 초반엔 공간적으로 흩어진(덜 겹치는) 뷰를 우선 선택하느라 손해를 보다가, 그 다양성이 나중에 갚아지는 패턴으로 보인다 — COVER 논문이 주장하는 메커니즘과 방향은 일치한다.
  • 시간 곡선은 완전히 다른 이야기를 한다 — coverage의 step당 이득은 실제로 있지만, selection 이벤트마다 발생하는 O(활성 뷰 × Gaussian) 전체 재계산 비용이 그 이득을 압도한다. 같은 wall-clock 예산에서는 random이 압승.
  • 후보 pool 노출은 두 run 모두 140/1,042(13%) — add_every_n_steps=200 (README 기본값)으로는 26,000 step 동안 전체 pool을 다 훑지 못한다. 두 run이 같은 스케줄을 쓰므로 비교 자체는 공정하지만, "COVER가 대규모 후보 pool에서 얼마나 잘 걸러내는가"까지는 이 설정으로 충분히 스트레스 테스트하지 못했다는 뜻이다.
  • Gaussian 수는 비슷한 자릿수(59만 vs 63만)라 이번엔 exp66 raw-init 비교에서 봤던 것 같은 "모델 용량 차이가 결과를 왜곡"하는 confound는 아니다.
  • 다음 결정 지점 — 이 레퍼런스 구현 그대로는 incremental VIGS 파이프라인에 이식할 근거가 약하다. 이식을 계속 고려한다면 핵심은 알고리즘이 아니라 "전량 재계산을 증분 업데이트로 바꿀 수 있는가"이고, VIGS 자체 render()가 돌려주는 radii(visibility mask)를 활용해 매 selection마다 새로 추가된 뷰의 coverage 기여분만 누적하는 방식이면 이 비용 구조를 근본적으로 피할 수 있어 보인다 — 다만 이건 아직 설계만 된 상태고 구현/검증 전.
