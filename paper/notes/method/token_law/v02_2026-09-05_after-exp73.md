# 유도 노트 — GPU-Token Admission Law (v02, 2026-09-05, exp73 반영)

원 출처: `context/research/vigs_slam_method_discussion_bullets.md` §2–§3
(= `notes/archive/discussion_bullets/CURRENT.md`)

## 제약식

```
κ [A(t) − A_0]_+  ≤  B_0 + γ S(t)      ∀t
```

| 기호 | 뜻 |
|---|---|
| `S(t) = Σ_{s≤t} b_s` | 시각 t까지 **실제로 완료된** dense-view Adam update 수 (B1 profile: b_s=1) |
| `A(t)` | t까지 admit된 누적 view 수 |
| `κ` | view 1장 admit에 요구하는 service-token 가격 |
| `γ` | 완료된 update 1회 → token 환산 계수 |
| `B_0` | 초기 service-token allowance |
| `A_0` | token 과금에서 제외하는 초기 bootstrap view 수 (`A_0=0`이면 전부 동일 과금) |

## 제약을 만족하는 최대 누적 admission

```
A*(t) = min( M(t),  A_0 + ⌊ (B_0 + γS(t)) / κ ⌋ )
```

`M(t)` = t까지 인과적으로 도착해 candidate가 될 수 있는 전체 view 수.
`min` 의 왼쪽은 **인과성**, 오른쪽은 **자원 제약**이다.

## 이번 시점의 quota

```
Q_t = min( |C_t|,  [ A*(t) − |A_{t^-}| ]_+ )
```

## 남은 token 형태 (등가)

```
B_t = B_0 + γS(t) − κ( |A_t| − A_0 ) ≥ 0
```
admission 1장마다 `B_t ← B_t − κ`.

## 왜 pool-size independent인가

`Q_t` 의 우변에 `|A_t|` 가 **누적 상한과의 차이**로만 들어가고,
admission **간격**은 `κ/γ` 로만 결정된다. candidate가 충분하면
정확히 `κ/γ` 개의 완료 update마다 1장이 들어온다.

대조: 기존 maturity gate는 `min_i n_i ≥ r` 이므로 pool이 커질수록 한 pass가 길어져
admission 간격이 `|A_t|` 에 비례해 늘어난다. **이것이 admission과 ordering을 결합시킨다.**

## exp73에서 구현한 no-prepurchase

pending candidate가 없을 때 token이 무한히 쌓이면 다음 interval 도착 시 burst admission.

| 정책 | 규칙 | 성질 |
|---|---|---|
| carry | 이미 완료한 service를 미래 candidate에도 사용 | burst 가능 |
| **no-prepurchase** | `C_t = ∅` 이면 `B_t < κ` 가 되도록 초과 token 폐기 | 보수적, burst 억제 |

exp73은 **no-prepurchase**를 고정했다. scheduler는 새 interval을 pending에 넣기 전에 지금까지
완료된 service delta를 먼저 소비하고, 그 시점에 pending candidate가 없으면 남은 credit을 0으로
만든다. 따라서 view가 도착하기 전에 수행한 compute가 미래 view를 선구매하지 않는다.

전역 seed 1장을 제외한 실제 유상 admission은 관측된 모든 526 poll에서

```
A_paid(u) = ⌊u / κ⌋
```

와 정수 오차 0으로 일치했다. 여기서 `u`는 exp73 logger가 집계한 token-service update 수다.
이는 구현된 counter와 admission law의 일치도를 뜻하며, 다른 GPU에서 wall-time당 admission rate가
같은 비율로 변한다는 B2까지 증명하지는 않는다.

## 기존 정책과 exp73의 정확한 차이

exp73은 maturity gate 하나만 제거한 ablation이 아니라 admission 정책 전체를 교체했다.

```
A_old = A_interval-bootstrap + A_gate-credit
A_exp73 = 1 + ⌊u / κ⌋
```

- 1253 baseline 두 run: `217+194=411`, `217+217=434`
- 1253 exp73 (`κ=22`) 두 run: `1+274=275`, `1+275=276`
- 305: `312+362=674 → 1+748=749`

따라서 1253의 pool 감소는 **gate 제거 효과가 아니라**, 무료 interval bootstrap 제거와
`κ=22` pacing이 함께 만든 결과다. 순수 gate 효과를 분리하려면 interval bootstrap을 유지한 채
maturity 조건만 제거하는 별도 arm이 필요하다.

## 현재 실측 경계

- 2개 장면·7개 gate-free run·526 admission poll에서 token-law 정수 오차 0.
- `κ=22`: 1253 두 run 평균 27.711 dB(baseline 대비 +0.003), 305 28.815 dB(−0.119).
- `κ=22`는 두 장면에서 재튜닝 없이 통과한 첫 engineering candidate이지 universal constant가 아니다.
- selection CV는 1253 `0.373→0.951`, 305 `0.470→0.942`로 악화했다. admission law만으로
  lifetime count 균등화가 해결되지는 않는다.

## 열린 질문

- `κ=22`의 두 장면 결과를 넘어, `κ`를 baseline·미래 정보 없이 정하는 online rule이 필요하다.
- `S(t)` 를 "성공한 replay step 수"로 셀 것인가 "measured GPU time"으로 셀 것인가.
  후자가 hardware adaptation 주장에 더 직접적이지만 측정 잡음이 들어온다.
- carry arm과 순수 gate-removal arm은 아직 실행하지 않았다.
