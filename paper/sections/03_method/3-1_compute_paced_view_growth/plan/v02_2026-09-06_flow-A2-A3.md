# 3.1 Compute-Paced View Growth — 무엇을 쓸 것인가 (v02, 2026-09-06)

> 한 줄 claim: **완료된 GPU service 가 학습 뷰의 증가 속도를 정한다.**
> 5문단 + `Slot placement.` run-in. 91줄 = 0.83 p.

## v01 에서 바뀐 것

v01 은 *"얼마나 빨리 늘릴 것인가"* 로 곧바로 들어갔다. **그 앞의 "왜 늘리려 하는가"가 없었다.**
그러면 독자는 pool 이 왜 있어야 하는지도 모른 채 규칙부터 받는다.

전제는 이미 근거가 있다 — `plan/claims/CURRENT.md` 의 **A2·A3, 둘 다 ✅**.

| | 주장 | 근거 |
|---|---|---|
| **A2** | keyframe 사이 RGB 는 버려지는 입력이 아니라 활용 가능한 mapping supervision 이다 | 동일 objective 에서 inter-keyframe 포함 view-set 이 keyframe-only 보다 held-out loss 낮음 (exp51/exp66) |
| **A3** | 최적 view-set 밀도는 compute budget 에 따라 달라진다 | exp66 viewset density — budget 별 최적점 이동 |

이 둘이 붙으면 논증이 선다:

> **더 쓰면 좋다(A2) → 그런데 공짜가 아니고 최적점이 예산 따라 움직인다(A3)
> → 그러면 예산에 맞춰 유입 속도를 정하는 규칙이 필요하다. 그게 C1 이다.**

## 논증의 흐름

```
P1   더 쓰면 좋다                        (A2)
      ↓ 그런데
P2   공짜가 아니다 → 속도를 정해야 한다       (A3)
      → baseline 의 답은 keyframe, 그건 속도를 집합 크기·하드웨어에 용접한다
      ↓ 그럼 무엇이 속도를 정해야 하나
P3   닫힌 고리인 계량은 완료된 service 뿐    ★ 기여
      ↓ 계량이 정해지면 나머지는 장부
P4   불변식 하나 → 상한이 따라옴
P5   현실이 두 군데서 어긋남 → 실현량, 폐기
      ↓ 그런데 어디에 둘지는?
run-in  +0.35% 뿐 → 병목은 몇 장이었다   (P2 로 회귀, 소절이 닫힌다)
```

## 문단 계약

| # | 하는 이야기 | 줄 | 근거·출처 |
|---|---|---:|---|
| **P1** | **왜 keyframe 밖까지 받아들이나.** keyframe 은 tracking 기준으로 골라진 표본이다. 같은 objective 에서 inter-keyframe 포함 view-set 이 held-out loss 가 낮다. 그 프레임들은 **이미 도착해 있어** 획득 비용이 0 이다 | 12 | **A2** |
| **P2** | **왜 keyframe 규칙이 틀린 답인가.** 쓰는 건 공짜가 아니다 — 받아들인 view 는 같은 수의 update 를 나눠 갖고, 최적 밀도가 예산 따라 움직인다. 즉 **속도를 정해야 한다.** baseline 은 그걸 keyframe 으로 정한다 [인용] → 속도가 집합 크기·하드웨어에 용접됨. ⚠ **dense 를 쓴다는 것 자체는 전제이지 주장이 아님**을 여기서 밝힌다 | 12 | **A3**, A2 경계 |
| **P3** | ★ **무엇을 계량하나.** wall-clock = 열린 고리 / iteration = 집합 크기와 커플링 / **완료된 GPU service = 유일한 닫힌 고리**. 계보: token bucket [RFC 2212] 인데 토큰이 경과 시간이 아니라 완료된 service 로 발행됨 = credit-based. **멈추면 계량도 멈추므로 burst 가 안 생긴다** — 시간 기반 bucket 이 depth cap 으로 막는 것을 우리는 채워지지 않아 막을 게 없다 | 16 | RFC 2212 |
| **P4** | **불변식 + 상한.** 쓴 것 ≤ 번 것 (1) → 거기서 상한 (2)가 따라온다. 바닥함수는 admission 이 정수라서, `min` 은 아직 도착 안 한 view 는 못 받아서. 자유 파라미터는 κ, γ 둘뿐 | 10 | |
| **P5** | **실현량 + 폐기 + 정책.** 후보 제약 → (3). pending 없으면 credit **폐기** — burst 두 번째 방벽이자 인과성의 근거(credit 이 interval 경계를 안 넘음). no-prepurchase 선언. §4 forward pointer, Fig.3 | 12 | **B3, B5** |
| run-in | **`Slot placement.`** quota 는 몇 장만 말한다. 어디에 둘지는 temporal maximin + interval water filling, 이득 +0.35%. **약하다는 사실을 논거로 쓴다** | 6 | |

수식 3개 9줄 + Fig.3 14줄 → **총 91줄 0.83 p.**

## 수식 순서 — 불변식이 먼저

```
(1) 불변식   κ(|A_t| − A₀) ≤ B₀ + γS(t)                     쓴 것 ≤ 번 것
(2) 상한     A*(t) = min(M(t), A₀ + ⌊(B₀+γS(t))/κ⌋)          ← (1)에서 따라옴
(3) 실현량   Q_t = min(|C_t|, [A*(t) − |A_{t⁻}|]₊)            도착·소멸 반영
```

v01 은 (2)를 먼저 던지고 불변식을 뒤에 붙였다. 그러면 상한이 **주어진 것**처럼 읽힌다.
불변식을 앞에 두면 상한이 그 **귀결**이 되어 독자가 한 줄을 따라가면 된다.
chen2026cover 의 "정확 → 완화 → 실용"을 축소한 형태이기도 하다.

**폐기 규칙은 식에 넣지 않고 산문으로 쓴다.** `B_t = B₀+γS(t)−κ(·)` 는 pending 이 있는 동안에만
유효한데, 그 조건을 식에 달면 지저분해지고 정작 중요한 *왜 버리는가*가 묻힌다.

## 문단이 5개인 이유

taming3dgs §3.2 는 4문단이고 우리 P2–P5 가 거기 1:1로 대응한다.
**한 문단이 더 드는 것은 P1 때문**인데, taming3dgs 는 *"왜 densify 하나"* 를 설명할 필요가 없는
반면 우리는 **keyframe 밖 프레임을 쓴다는 것 자체가 설명이 필요한 선택**이기 때문이다.
A2·A3 라는 근거가 있으므로 정당한 추가다.

## 문단마다 **말하면 안 되는 것**

| 문단 | 금지 | 근거 |
|---|---|---|
| P1 | pool-independence 를 실증된 것처럼 | B1 ⚠ — pool 크기를 직접 sweep 한 실험이 아님 |
| P2 | dense 사용 자체를 기여로 | A2 경계 |
| **P3** | **하드웨어 적응을 실측 주장으로** | **B2 ▶ 미검증 (P02 대기).** *"속도가 하드웨어와 무관"* 은 **설계 성질**로만 쓴다 |
| P4 | κ 를 보편 상수처럼 | exp59 전이 실패 전례 |
| P5 | no-prepurchase 가 carry 보다 낫다 | B5 경계 — 정책 선택과 비교 우위를 구분 |

★ **P3 가 제일 위험하다.** 이 절의 핵심 논거인데 하필 증거가 아직 없다.
문장에서 *설계상 그렇다* 와 *측정했다* 가 구별되어야 하고, §4 forward pointer 가 그 역할을 한다.
