# 3.1 Pool-Independent GPU-Token Admission (★C1) — 무엇을 쓸 것인가 (v01, 2026-09-05)

> 한 줄 claim: **완료된 GPU service만으로 admission을 결정해 pool 크기와 무관한 유입률을 만든다**
> ⚠ claim boundary: exp72에서 pool-independence는 **실패 판정**. P01/P02 통과 전 "we show"로 쓰지 말 것.

## 이 절의 역할

§3.0이 결정을 셋으로 쪼갰다면, 이 절은 그중 **cardinality**를 푼다. 핵심 논지는
"dense frame을 쓸지 말지"가 아니라 **"지금까지 실제로 확보한 GPU service로 감당 가능한
supervision 개수가 얼마인가"** 이며, 그 답이 pool 크기에 의존하면 admission과 ordering이
결합되어 어느 쪽 효과인지 분리할 수 없게 된다. 이 절이 없으면 §3.3의 ablation이
"순서를 바꿨더니 pool도 같이 바뀐" 교란 실험이 된다 — 실제로 exp72가 그랬다.

## 반드시 넣을 내용

- [ ] **Motivation 3문장**
  - 고정 dense FPS는 입력률만 규정하고 mapper가 그걸 학습할 수 있는지는 반영하지 않는다
  - 전부 즉시 넣으면 계속 커지는 training set에 update가 분산된다
  - 기존 maturity gate(`min_i n_i ≥ r`)는 pool이 커질수록 한 pass가 길어져 admission과
    ordering을 결합시킨다
- [ ] **Deterministic token law** (식 4개)
  - `S(t) = Σ_{s≤t} b_s` — 실제로 **완료된** dense-view Adam update 수 (B1 profile에서 b_s=1)
  - `A*(t) = min( M(t), A_0 + ⌊(B_0 + γS(t)) / κ⌋ )`
  - `Q_t = min( |C_t|, [A*(t) − |A_{t^-}|]_+ )`
  - `B_t = B_0 + γS(t) − κ(|A_t| − A_0) ≥ 0`
- [ ] **기호 표** — S, B_0, γ, κ, A_0, M(t), C_t, A_t. 본문 표 1개로.
- [ ] **정의상 만족하는 성질 4개** (증명이 아니라 정의의 직접 귀결임을 명시)
  - pool-size independence: admission 간격이 `κ/γ`로 결정됨
  - hardware adaptation: 같은 wall time에 S(t)가 2배면 admission도 2배
  - causality: 완료된 update와 이미 도착한 C_t만 사용
  - resource feasibility: 모든 prefix에서 `κ[A(t)−A_0]_+ ≤ B_0 + γS(t)`
- [ ] **token 정책 선택** — carry vs no-prepurchase 중 **하나로 고정**하고 이유를 쓴다
  - 현재 후보: no-prepurchase (`C_t = ∅` 이면 `B_t < κ` 가 되도록 초과 token 폐기)
  - 둘 다 "미래 compute를 당겨쓰지 않음"은 만족. **차이는 admission burst 특성**
  - → P01에서 A/B 후 확정
- [ ] **bootstrap 규칙** — 새로 닫힌 keyframe interval마다 첫 dense view 1장은 즉시 편입.
  admitted view가 없어 replay가 안 돌고, replay가 없어 credit도 안 생기는 초기 교착 방지
- [ ] **deadline guard** — `t_wall + δ̂_t ≤ d̂_{t+1}` 일 때만 replay 1 step 시작.
  이건 admission score가 아니라 **실행 가능성 검사**임을 명시 (§4.6과 연결)

## Contribution으로 **주장하지 않을** 것

- dense frame을 사용한다는 사실 자체 (A2 — 이미 알려진 것)
- 최적 cardinality의 닫힌 형태나 이론적 optimum (A3의 경계)
- 전역 objective의 최적해를 푼다는 것 — 이건 hard constraint를 **정확히 만족**시키는
  deterministic controller다
  (근거: [`../../../../plan/claims/CURRENT.md`](../../../../plan/claims/CURRENT.md) §B)

## 기존 maturity gate와의 차이 (표로)

| | 기존 exp69/exp72 | 제안 token |
|---|---|---|
| admission 조건 | `min_i n_i ≥ 2` (모든 view가 2회) | `S(t)` 만 |
| pool이 커지면 | 한 pass가 길어져 admission이 느려짐 | 무관 |
| scheduler를 바꾸면 | cardinality도 바뀜 (교란) | 같은 S(t)면 같은 cardinality |
| count n_i 의 역할 | admission + ordering 양쪽 | **ordering에서만** |

이 표가 §3.3 ablation의 정당성이다.
