# v04 생성 프롬프트

내장 imagegen 사용. 기존 이미지를 편집하지 않고 기능별 구조를 가진 새 구도를 생성한다. 모든 장면은 설명용이다.

```text
Use case: infographic-diagram.
Asset: original academic overall-pipeline figure concept for a two-page robotics/3D Gaussian mapping paper. Create a NEW composition, not an edit of a prior diagram. Wide landscape about 2.2:1, high resolution, pure white ground, polished conference-paper figure craftsmanship. Dense with useful visual evidence, disciplined spacing, crisp dark typography, no presentation title or decorative banner. NOT a flowchart made of rectangles. No glossy UI, cards, heavy shadows, rounded boxes, ornamental icons, or paragraph text.

Organizing principle: observations become training views, which repeatedly improve a shared Gaussian map. Three gently tinted, borderless functional territories left-to-right, headings exactly "Online observations", "Training-view management", "Gaussian map optimization". Widths roughly 21%, 35%, 44%. Subtle neutral / warm / cool background washes fading to white; preserve clean gutters. Use orange for (a), blue for (b), muted violet for (c); existing frontend neutral gray. Compact labels large enough for print.

LEFT territory:
Draw a graceful small camera trajectory with three wireframe camera frustums above a horizontal filmstrip of five distinct perspective views of the SAME simple indoor room (desk, chair, walls). These are illustrative, not claimed experimental photos. Distinguish two keyframes by dark outlines; intervening views thin outlines. Labels "RGB + IMU", "Keyframes", "Intermediate views". A modest gray frontend symbol (one small neutral block is allowed) labeled "Online frontend" yields "Poses" and a small colored depth-map thumbnail labeled "Keyframe depth". Do not depict a depth sensor. Keep this context area visually subordinate.

MIDDLE territory:
Main object is a substantial compact two-row array of image thumbnails, a retained training-view pool, not another box. Label "Retained training views". Above its left edge show two additional arrived image thumbnails just outside the pool, with an orange admission bracket and a short inward arrow. Label "(a) View Growth" and smaller "Admit as updates complete". All pictured candidate images have already arrived; no future frames, no discarding earlier images.
Within the SAME pool highlight two different thumbnails in blue, with a tiny strip of unequal blue probability bars aligned beneath several thumbnails (no numeric counts/probabilities). Label "(b) View Sampling", smaller "Selection counts + randomness". Show a COPY of one selected thumbnail exiting right toward optimization, labeled "One view per update"; selected originals remain in pool. Sampling means stochastic preference for under-selected views, not deterministic least-count or loss scoring. No separate Growth and Sampling module boxes. Pool should occupy most of this territory.

RIGHT territory:
Hero object, occupying upper-middle right: a large legible oblique 3D cutaway of the same room represented by translucent colored anisotropic Gaussian ellipses on walls, desk, chair. Label "Shared Gaussian map". This is a persistent state, not just a final output screenshot. A small gray route across the TOP of the composition from frontend poses/depth to this map is labeled "Geometry-based initialization"; it bypasses view admission and selection.
Next to/below map, compact paired actual illustrative image tiles labeled "Rendered RGB" and "Observed RGB", joined by a minimal comparison symbol with label "Appearance loss". The selected-view route supplies observed RGB and viewpoint for rendering the current map. A clear local render/optimize loop returns to the SAME map, with labels "Render" and "Update". Map -> Rendered RGB -> appearance loss -> Update -> same map.
At lower-right embed a violet geometric inset INSIDE this optimization territory labeled "(c) Geometry supervision". Show one camera ray traversing translucent Gaussian ellipses toward an observed surface band; labels only "Free space" and "Surface". Show some faint off-surface opacity as the constrained quantity; no hard-deletion X symbols, no before/after performance claims. A thin violet/gray evidence path from frontend Keyframe depth runs cleanly along bottom perimeter into this inset, never through the view pool. The inset contributes "Geometry loss" into the SAME Update as appearance loss, not a postprocessing stage and not the next stage after sampling. Keep (c) smaller than map, roughly 1/4 of optimization territory.

Feedback: ONE clearly routed orange dashed return arrow from completed Update along an uncluttered corridor back to (a), labeled "Completed updates". Local blue small return arrow from selected-copy action back to probability strip labeled "Selection history". Solid connections mean data/loss, dashed connections mean scheduling feedback. No arbitrary crossed connectors, no double-headed arrows, no arrow entering labels, no duplicated maps, no map-to-tracking feedback. Keep arrows few and thin, meaningful and readable. Gray initialization top perimeter and depth bottom perimeter must remain distinct.

Visual balance: the room map, view array, and observation filmstrip carry the composition. Main objects fill space; arrows and labels support them. Align all three headers, use consistent sans-serif type and line weights. Short labels only, no equations, legends longer than one line, invented metrics, benchmark names, speedup claims, logos, or fake results. Tiny discreet footer exactly "Illustrative concept — not experimental results". This is an elegant academic scientific illustration, not a business infographic.
```
